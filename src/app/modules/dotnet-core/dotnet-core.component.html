ASP.NET (Core + MVC)

.NET Core is a free, open-source, cross-platform framework for building modern applications, including web, desktop, mobile & cloud-based apps. It allows developers to write code that can run on multiple platforms (Windows, MacOS, Linux) & is known for its performance, scalability & flexibility.

1. Which .NET Core architecture do you use?

I work in a project that follows Repository pattern in 3-tier architecture.

a. Presentation Layer (Controller): Handles incoming HTTP requests, validates them & returns responses.

b. Business Logic Layer (Services): Contains the core business logic & application rules. It processes the data between the presentation layer & the data access layer.

c. Data Access Layer (Repository Layer): Manages interaction with the database.

2. What is Repository Pattern, and how does it relate to Entity Framework?

The Repository pattern is a design pattern used to abstract the data-access layer of an application, providing a clean separation between the business logic & data storage.

Entity Framework (EF) is an Object-Relational Mapping (ORM) framework that interacts directly with the database.

The Repository pattern can be used on top of EF to hide EF's direct database access logic, providing a more testable & flexible interface.

3. What is the purpose of Program.cs file in .NET Core?

The Program.cs file in .NET Core is the entry point of an application. It's main purpose is to configure & start the application.

It sets up the host & defines the necessary configuration, services & middleware required to run the application.

4. What is the difference between Authentication & Authorization?

Authentication Authorization
Purpose: Verifies the identity of a user or system Purpose: Determines what resources a user or system is allowed to access after authentication.
Process: Users provide credentials (eg. username, password, biometrics) to prove who they are. Process: Once authenticated, the system checks if the user has permission to perform certain actions (eg. read, write, modify)
Example: Logging in to a website with username & password. Example: After logging in, a user may be allowed to view certain pages but not modify them.
Focus: Answers the question: "Who are you?" Focus: Answers the question: "What are you allowed to do?"

5. What are the different ways for authentication in .NET Core?

There are 3 ways for Authentication in .NET Core which are as below:

a. Cookie-based Authentication:

Stores authentication information in a cookie. It's often used in web-applications where the server generates a cookie after a user logs in.

Use Case: Tradionatiol ASP.NET Core MVC web-applications.

Example: Signin Manager creates a cookie for authenticated users, which is then sent with subsequent requests.

b. JWT (JSON Web Token) Authentication:

A stateless authentication method that uses a token (JWT) to verify a user's identity. The token is sent in the HTTP headers (typically Authorization: Bearer).

Use Case: Common in API-based applications & SPA (Single Page Applications).

Example: After login, the server issues a JWT which the client uses for subsequent requests.

c. OAuth2 & OpenID Connect:

OAuth2 is an authorization protocol, and OpenID Connect extends OAuth2 for Authentication.

Use Case: It's often used for integrating external identity providers like Google, Facebook or Microsoft.

Example: Web Apps or APIs that rely on third-party authentication.

6. Explain the difference between controller & an API.

Controller can hold a collection of APIs to handle HTTP requests & process user inputs.

API defines a single endpoint which can be used by other software applications to request/retrieve data.

7. What is Inversion of Control?

Inversion of Control (IoC) in .NET is a design principle where control over object creation & dependencies is transferred from the class to an external entity, typically an IoC container.

Principle: Don't call me; we will call you.

The main class should not have a concrete implementation of an aggregated class, rather, it should depend on the abstraction of that class.

8. What is Dependency Injection in C#?

Dependency Injection (DI) is a C# design pattern that implements Inversion of Control (IoC) by allowing an object's dependencies to be injected at runtime rather than hard-coded.

This promotes loose coupling, making code more modular, testable & maintainable.

9. Why do we need Dependency Injection?

Without Dependency Injection, a class creates its own dependencies using the 'new' keyword, which tightly couples it to specific implementations.

DI allows the dependencies to be passed in, making the class less dependent on concrete types.

10. How to create Dependency Injection in .NET Core?

a. Define your Services: First, create the services that we need to inject. These typically implement an interface.

b. Register services in the DI container: In .NET Core, services are registered in the Startup Class (or Program class in .NET 6+). We register the services in the 'ConfigureServices' method.

c. Inject services into Consumers: To use the services, inject them into the classes that need them.

11. In how many ways, can we achieve Dependency Injection in C#?

In C#, Dependency Injection can be achieved in 3 ways, which are as below:

a. Constructor Injection:

Dependencies are passed via the class constructor.

Constructor Injection is best for mandatory dependencies & promotes immutability.

b. Property Injection:

Dependencies are set through public properties.

Property Injection is best for optional dependencies but it may lead to runtime 'NullReferenceException' if not set properly.

c. Method Injection:

Dependencies are passed as parameter to a method.

Method Injection is best when dependency is used only in 1 method.

12. Explain AddSingleton, AddScoped & AddTransient.

AddSingleton: Creates a single instance of the service for the entire application lifetime.

AddScoped: Creates a new instance of the service per request (or per scope).

AddTransient: A new instance is provided every time the service is injected.

14. What is the use of Middleware in .NET Core?

Middleware is used to:

a. Handle Requests: Process incoming HTTP requests.

b. Modify Responses: Modify or generate HTTP responses.

c. Perform Actions: Execute logic such as authentication, logging, or error handling.

d. Pipeline: Middleware is configured in specific order within the request pipeline. Each middleware component has access to the HTTP context & can either handle the request or pass it to the next component in the pipeline.

15. What is the difference between Middleware & Filters?

Middleware & Filters are both used to add custom logic into the request processing pipeline, but they operate at different levels & have different purposes.

Here is a clear comparison of the two:

a. Middleware

Scope: Application-wide (entire HTTP pipeline)

Location: Configured in Program.cs (or Startup.cs in older versions)

Middleware can be used to handle cross-cutting concerns for all requests, like

  • Error handling
  • Logging
  • CORS
  • Authentication

b. Filters

Scope: MVC/Web API pipeline (Controller/action level)

Location: Applied to controllers or actions

Filters can be used for logic specific to controller/action execution, such as

  • Authorization
  • Validation
  • Result formatting
  • Exception Handling (specific to MVC)

17. What is Rate Limiter?

In .NET, a rate limiter is a mechanism that restricts the number of requests a client can make to a resource within a specific time frame.

The rate limiter middleware is added to the application's request pipeline.

If the request is within the allowed limit, the middleware grants a "permit" and allows the request to proceed.

If the limit is exceeded, the middleware rejects the request, typically returning a 429 "Too Many Requests" HTTP status code.

20. What is the difference between IEnumerable & IQueryable?

"Enumerable" works with a data already in memory, while "Queryable" can query data from a remote source like a database.

When using "Enumerable", the entire collection is loaded into memory before filtering, while "Queryable" allows you to build a complex query that is executed on the server side, only retrieving the necessary data.

"Enumerable": Ideal for iterating through small to medium-sized in-memory collections.

"Queryable": Best for complex queries against large datasets stored in a database.

21. What is serialization & why is it used in C#?

Serialization in C# is the process of converting the state of an object into a transmittable or storable format, like a stream of bytes, JSON, or XML.

This allows you to save an object's state to a file, database, or send it over a network, and then reconstruct it later.

Essentially, it transforms complex objects into a simpler, portable form.

In C#, serialization is typically achieved through classes like BinaryFormatter, JsonSerializer, or XmlSerializer.

"throw": Preserves the original exception's stack trace, providing a complete picture of the exception's origin.

"throw ex": Resets the stack trace, potentially losing the original exception's context & makes debugging harder.

C# extension method is a special kind of static method that is called as if it was an instance method on the extended type.

25. What are Action Filters? How many types of action filters are there in MVC?

Action filters are attributes that can be applied to Controllers & Action Methods.

They allow you to intercept and run custom code at different points during the request processing lifecycle.

Types of Filters

1. Authorization Filter: Runs first, before anything else. Used for checking user permissions or authentication.

2. Action Filter: Runs before and after an action method executes. Useful for logging, timing, modifying parameters or results.

3. Result Filter: Runs before and after the action result is executed (e.g., ViewResult).

4. Exception Filter: Handles unhandled exceptions thrown by action methods or results.

ASP.NET Core MVC

29. What is ASP.NET Core MVC and how does the request flow work?

ASP.NET Core MVC is a framework for building web applications using the Model-View-Controller design pattern. It separates an application into three distinct roles so that UI, business logic, and data don't get tangled together.

Think of it like visiting a restaurant:

  • Customer (Browser): Makes an HTTP Request to order something.
  • Controller (The Waiter): Receives the request, decides which kitchen station needs to work on it, and carries the finished dish back to the customer.
  • Model (The Kitchen & Ingredients): Holds the data, runs business calculations, and talks to the database.
  • View (The Plated Dish): The visual presentation (HTML/CSS) created using Razor syntax that the customer sees and interacts with.

The Request Flow in 4 simple steps:

  1. An HTTP request arrives and Routing maps the URL to a specific Controller and Action method.
  2. The Controller executes, talks to services or the database to fetch or save Model data.
  3. The Controller packages the data and hands it over to the View.
  4. The Razor View engine renders the final HTML and sends it back to the user's browser.

30. What is the difference between ActionResult and IActionResult?

Both are used as return types for controller action methods in ASP.NET Core, but they serve slightly different purposes:

  • IActionResult: An interface. It provides maximum flexibility because an action can return any result implementing it — such as View(), Json(), Ok(), BadRequest(), or NotFound().
  • ActionResult<T>: A generic class introduced in .NET Core 2.1. It lets you return either a specific model type T (e.g. Product) or any HTTP ActionResult (like NotFound()).

Why does this distinction matter in interviews? When building APIs, IActionResult does not tell Swagger/OpenAPI what exact data type is returned unless you annotate the action with [ProducesResponseType]. With ActionResult<T>, the return type is strongly typed, so Swagger automatically documents the response schema and you get compile-time type checking!

Feature IActionResult ActionResult<T>
Type Interface (contract) Generic class wrapper
Type Safety Low (returns general results) High (knows exact model type T)
Swagger/API Docs Needs explicit attributes Infers response schema automatically
Primary Use MVC Views & general actions RESTful Web APIs

31. How do you pass data from Controller to View? (ViewBag vs ViewData)

Both ViewData and ViewBag are used to pass small, temporary data from a Controller to a Razor View for the current HTTP request only. Once the request finishes, both are cleared.

  • ViewData: A dictionary of objects, accessed with string keys like ViewData["Title"] = "Home". Because it stores values as object, you must explicitly typecast non-string values when reading them in the View (e.g., (int)ViewData["Count"]).
  • ViewBag: A dynamic wrapper around ViewData using C# dynamic properties (ViewBag.Title = "Home"). Behind the scenes, it writes to and reads from the exact same dictionary as ViewData! The syntax is cleaner and no typecasting is required.
Feature ViewData ViewBag
Underlying Type ViewDataDictionary DynamicViewDataException wrapper
Syntax ViewData["Key"] ViewBag.Key
Typecasting Required for non-string types Not required (resolved at runtime)
Compile-time Check No (runtime checks) No (runtime resolution)
💡 Senior Developer Tip: In real production apps, avoid both! Always prefer Strongly Typed ViewModels (e.g. @model UserDashboardViewModel) because you get compile-time error checking, refactoring support, and full IntelliSense autocomplete.

32. What is TempData and how does it work?

While ViewData and ViewBag are destroyed the moment the current request ends, TempData survives across HTTP redirects (from one request to the very next request).

Classic Real-World Scenario: When a user submits a form (e.g., "Create Account"), the controller saves the data and redirects the browser to the login or list page using RedirectToAction("Index"). A redirect triggers a brand new HTTP request, so ViewBag/ViewData would be empty! TempData is built specifically to hold flash messages like "Account created successfully!" across that redirect.

How TempData works internally:

  • It stores data temporarily using Cookie-based storage or Session state behind the scenes.
  • The Golden Rule: Once a TempData key is read during a request, it is marked for deletion and gets removed at the end of that request.

33. What is the difference between Keep() and Peek() in TempData?

Because reading a TempData key normally marks it for deletion at the end of the request, C# provides two special methods when you want to read it and still keep it alive for future requests:

  • Peek("Key"): Reads the value without marking it for deletion. Think of it like looking through a window — you see the data, but you don't consume or touch it. The key stays alive for the subsequent request automatically.
  • Keep("Key"): If you already accessed TempData["Key"] normally (which marked it for deletion), calling TempData.Keep("Key") retains it and removes the deletion mark. You can also call TempData.Keep() with no arguments to keep all keys alive.
Feature Peek() Keep()
Purpose Reads data without marking it for removal Restores/preserves a key that was already read
When to use When you know upfront you want to inspect without consuming When you read the key first, then decide based on logic to keep it
Preserve all keys Must pass specific key TempData.Keep() preserves all keys

34. What are Cookies and how do you use them in ASP.NET Core?

A Cookie is a small piece of data stored directly on the user's web browser. Every time the browser makes a request to your server, it automatically attaches the cookies in the HTTP request headers.

Unlike Sessions (which live on the server and expire quickly), Cookies can persist across browser restarts for days, months, or years. They are commonly used for remembering user preferences (e.g. Dark Mode, language selection) or storing persistent authentication tokens ("Remember Me").

Key Cookie Security Options (Frequently asked in interviews):

  • HttpOnly = true: Prevents client-side scripts (JavaScript) from accessing the cookie via document.cookie. This is vital to protect against Cross-Site Scripting (XSS) attacks.
  • Secure = true: Instructs the browser to only transmit the cookie over encrypted HTTPS connections.
  • SameSite = SameSiteMode.Strict / Lax: Controls whether the cookie is sent with third-party cross-site requests, mitigating Cross-Site Request Forgery (CSRF) attacks.

35. What is a Partial View and when should you use it?

A Partial View is a reusable Razor file (.cshtml) that renders a fragment of HTML inside another view. It does not have its own _Layout.cshtml — it is simply a component of a larger page.

Think of it like a reusable UI building block. If you have an e-commerce website where a product card appears on the Home page, Category page, Search results, and Wishlist, you don't duplicate the markup four times. You create _ProductCard.cshtml once and include it wherever needed.

Benefits of Partial Views:

  • Code Reusability (DRY): Change the markup in one file, and every page updates automatically.
  • Cleaner Views: Breaks large, 1000-line Razor files into small, easily maintainable sections.
  • AJAX Updates: Perfect for returning just a portion of a page during an AJAX call without re-rendering the whole page layout.

36. What is the difference between a Partial View and a View Component?

This is a favorite senior .NET interview question. While both render reusable HTML chunks, they work very differently under the hood:

  • Partial View: A "dumb" template. It has no C# controller logic of its own. It can only display data that the parent page explicitly passes to it. If the parent page doesn't have the data, the partial view cannot render it.
  • View Component: A mini-controller paired with a view. It has its own C# class inheriting from ViewComponent, its own asynchronous method (InvokeAsync), and can use Dependency Injection to query a database or call external APIs completely independently of the parent page!

Real-World Example: Imagine a shopping cart icon in your website's header showing the count of items in the cart. The header appears on every single page (even the "About Us" and "Contact Us" pages). With a Partial View, every single controller in your app would have to fetch the cart count and pass it. With a View Component, the component queries the cart service by itself, keeping your controllers completely clean!

C# Logic None (pure Razor template) Has its own C# class & logic
Dependency Injection No (depends on parent model) Yes (can inject services directly)
Coupling with Parent Tightly coupled to parent's data Fully autonomous and decoupled

37. What is Model Binding and ModelState.IsValid?

Model Binding is the magical bridge in ASP.NET Core that automatically takes incoming HTTP data (form POST values, query string parameters ?id=10, route values, or JSON body) and converts them into C# objects and parameters in your action method. You don't have to write manual parsing code like Request.Form["Email"].

ModelState.IsValid checks whether the incoming data passed all the validation rules you configured on your model (using Data Annotations such as [Required], [EmailAddress], [StringLength], or custom validators).

  • If any rule fails (or a data type mismatch happens, like entering letters into an int field), ModelState.IsValid becomes false.
  • The controller can immediately redisplay the view, and Razor helpers (like <span asp-validation-for="...">) automatically display user-friendly error messages next to the inputs.

38. What is the difference between Conventional Routing and Attribute Routing?

Routing is the mechanism that matches incoming HTTP request URLs to the specific Controller and Action method that handles them. ASP.NET Core supports two ways to define routes:

  • Conventional Routing: Configured centrally in Program.cs using a URL template pattern, typically {controller=Home}/{action=Index}/{id?}. The framework extracts the controller and action names directly from the URL segments.
  • Attribute Routing: Configured directly above Controllers and Action methods using attributes like [Route("products")] and [HttpGet("{id:int}")].
