Architecture and Fundamentals

Core software engineering lifecycles, design principles, web communication protocols, and architectural patterns essential for scalable, maintainable applications.

1. What is SDLC (Software Development Life Cycle) and what are its key phases?

The Software Development Life Cycle (SDLC) is a structured, step-by-step framework used by development teams to design, build, test, and maintain high-quality software efficiently.

It provides a roadmap for producing software that meets customer expectations within time and budget constraints.

Key Phases of SDLC:

Although frameworks vary, the SDLC generally consists of these seven stages:

  1. Planning: Defining the scope, goals, and resources for the project.
  2. Requirement Analysis: Gathering detailed functional and non-functional requirements from stakeholders.
  3. Design: Creating the software architecture, user interface (UI), and system interfaces.
  4. Development/Implementation: Coding or actual creation of the software based on design documents.
  5. Testing: Identifying bugs and verifying that the software meets requirements.
  6. Deployment: Releasing the final software to the production environment for user access.
  7. Maintenance: Ongoing support, updates, and bug fixes to ensure the system remains functional.

2. What are the SOLID Principles?

The SOLID principles are five design guidelines that help .NET developers create software that is easy to maintain, scale, and test.

a) Single Responsibility Principle (SRP)

  • Principle: "A class should have only one reason to change."
  • Concept: Each class should focus on a single piece of functionality.
  • Example: In .NET: Instead of a single UserService that handles validation, database saving & email notifications, you should split these into UserValidator, UserRepository & EmailService.

b) Open/Closed Principle (OCP)

  • Principle: "Software entities should be open for extension, but closed for modification."
  • You should be able to add new functionality without changing existing, tested code. In .NET, we achieve this using abstract classes or interfaces.

c) Liskov Substitution Principle (LSP)

  • Principle: "Objects of a superclass should be replaceable with objects of its subclasses without breaking the application."
  • If Class B inherits from Class A, you should be able to pass B into any method that expects A without getting unexpected errors (like NotImplementedException).

d) Interface Segregation Principle (ISP)

  • Principle: "Clients should not be forced to depend on methods they do not use."
  • Violation: An IMachine interface with Print(), Fax(), and Scan(). A basic printer class is now forced to implement Fax() even if it can't do it.
  • Solution: Break it into IPrinter, IFax, and IScanner.

e) Dependency Inversion Principle (DIP)

  • Principle: "High-level modules should not depend on low-level modules. Both should depend on abstractions."
  • This is the foundation of Dependency Injection (DI) in .NET Core. Instead of a class creating its own "helper" objects (using new), the helpers are "injected" via the constructor.
c#
// Low-level module (the detail)
public interface IMessageService { void Send(string msg); }

// High-level module (the logic)
public class Notification
{
    private readonly IMessageService _service;
    
    // The class doesn't care if it's EmailService or SmsService
    public Notification(IMessageService service) 
    {
        _service = service;
    }
}

3. What is the difference between HTTP and HTTPS? Why was HTTPS introduced and who introduced it?

HTTP (HyperText Transfer Protocol) is the basic communication language of the web. When you type a URL into your browser, HTTP is the protocol that fetches HTML pages, images, and API data from the web server.

The Problem with Plain HTTP:
HTTP transmits all communication in plain text. Think of HTTP like sending a postcard through the mail—anyone handling it along the route (internet service providers, public Wi-Fi routers, or hackers using packet-sniffing tools) can read your passwords, credit cards, and private messages.

What is HTTPS?
HTTPS (HyperText Transfer Protocol Secure) is HTTP with a security guard. It is the exact same HTTP protocol, but wrapped inside an encryption layer called SSL/TLS (Secure Sockets Layer / Transport Layer Security).

Think of HTTPS like putting that message inside a locked, tamper-proof steel box. Only the sender (your browser) and the intended recipient (the server) have the secret keys to lock and unlock it. If anyone intercepts the data in between, all they see is random unreadable gibberish.

Who Introduced HTTPS and When?

  • Netscape Communications introduced HTTPS in 1994 for their flagship Netscape Navigator web browser.
  • They developed the SSL (Secure Sockets Layer) protocol to protect sensitive data for the very first wave of e-commerce and online payments on the internet.
  • Over time, SSL was updated and succeeded by modern, stronger encryption standards known as TLS (Transport Layer Security), though people still casually refer to them as "SSL certificates".

Why was HTTPS Introduced? (The 3 Pillars of HTTPS)

  • 1. Encryption (Privacy & Secrecy):
    Guarantees that no eavesdropper or hacker on the network (especially on public Wi-Fi at airports or cafes) can read sensitive data like credit card numbers, passwords, or personal chats.
  • 2. Data Integrity (No Tampering):
    Ensures the data cannot be modified, corrupted, or injected with malicious scripts or fake ads while in transit between the server and the browser.
  • 3. Authentication (Identity Verification):
    Uses a digital SSL/TLS Certificate signed by a trusted Certificate Authority (CA) to prove you are actually communicating with the legitimate website (e.g. your real bank) and not a fake phishing imposter website.

4. What is REST and RESTful API? Explain the key REST principles.

REST stands for Representational State Transfer. It is not a protocol, language, or library; it is an architectural style (a set of guidelines and design rules) for building web services that communicate over HTTP.

What is a RESTful API?
A RESTful API is an API that adheres to these REST guidelines. In simple terms:

  • Everything is treated as a Resource (e.g., User, Product, Order).
  • Each resource is identified by a unique, clean URI / URL using nouns (e.g., /api/users or /api/orders/101 instead of /api/getOrders).
  • Data is exchanged using standard lightweight formats like JSON.
  • Standard HTTP Verbs are used to perform CRUD operations on the resources:
    • GET - Retrieve/read data (e.g., GET /api/users/5)
    • POST - Create a new resource (e.g., POST /api/users)
    • PUT - Replace / update an existing resource completely (e.g., PUT /api/users/5)
    • PATCH - Partially update specific fields of a resource (e.g., PATCH /api/users/5)
    • DELETE - Remove a resource (e.g., DELETE /api/users/5)

Key REST Principles (Constraints):

An API is strictly RESTful if it follows these 6 core principles:

1. Client-Server Architecture

  • The frontend (Client) and backend (Server) are completely separated.
  • The client handles UI and user experience, while the server handles business logic and data storage. Both can evolve independently without breaking each other as long as the API contract stays intact.

2. Statelessness (Crucial)

  • The server does not store any client session state between requests.
  • Each request from client to server must contain all necessary data to process it (e.g., authentication token in headers, payload in body). Every request stands on its own.

3. Cacheability

  • Responses must explicitly state whether they can be cached or not (using HTTP headers like Cache-Control).
  • Caching eliminates unnecessary calls to the server for identical data, drastically improving speed and scalability.

4. Uniform Interface

  • Provides a consistent and predictable way to interact with resources across any client (web, mobile, third-party):
  • Resources are named with clear nouns (e.g., /api/customers).
  • Standard HTTP status codes are used to communicate success or error (e.g., 200 OK, 201 Created, 404 Not Found).

5. Layered System

  • The client does not need to know whether it is connected directly to the origin server or through intermediate layers like an API Gateway, Load Balancer, or Reverse Proxy.
  • This allows adding security and caching layers without impacting client applications.

6. Code on Demand (Optional)

  • Servers can optionally extend client capabilities by sending executable code (such as JavaScript). This is optional and rarely used in pure REST APIs.

5. What is Monolithic Architecture and Modular Monolithic Architecture?

Monolithic Architecture is a software design pattern where the entire application is built as a single, cohesive unit.

The entire application resides in one solution (e.g., a single Visual Studio Solution), often organized into folders like /Controllers, /Models, and /Services for separation of concerns.

Drawbacks:

In a monolith, all components share the same memory space and resources.

  • a) Resource Exhaustion: If "View A" has a bug that causes an infinite loop or leaks memory, it consumes the CPU/RAM of the entire process. Because "View B" is running in that same process, it will slow down or crash as well.
  • b) Shared Dependencies: If "View A" and "View B" both use the same DbContext or a shared Service, and "View A" causes a database deadlock or crashes the Service, "View B" will fail immediately because it relies on that same shared "brain."

Advantages:

  • a) Simplicity: Easier to develop, test, and debug initially as all code is in one place.
  • b) Simplified Deployment: Only one unit needs to be deployed to a server.

What is Modular Monolithic architecture?

In a Modular Monolith, you still use Controllers, Services, and Repositories, but you wrap them inside strictly isolated modules based on the business domain (e.g., a "MatchModule" and an "EmployeeModule").

Key Differences:

  • a) Strict Boundaries: The MatchModule has its own Services and Repositories. The EmployeeModule cannot see them.
  • b) Communication: If the MatchModule needs data from an Employee, it cannot call the EmployeeRepository. It must call a public Interface/API exposed by the EmployeeModule.
  • c) Database Separation (Logical): Even if they share one SQL Server, you might use different Schemas (e.g., match.Matches vs hr.Employees) to ensure one module doesn't "reach into" the other's tables.
  • d) Migration Path: If "Match" module ever grows too big, you can simply right-click that folder, move it to a new project, and turn it into a Microservice in a single afternoon.

Advantages of Modular Monolith:

  • a) Clear Separation & Maintainability: Enforces domain boundaries and prevents tightly-coupled "spaghetti code", making modules easier to understand, test, and maintain.
  • b) Low Operational Overhead: Delivers clean microservice-like boundaries without the complexity of network latency, distributed transactions, or managing multiple CI/CD pipelines.
  • c) Smooth Migration to Microservices: Modules can be extracted into standalone microservices easily when scaling or team size demands it, without major codebase rewrites.

Drawbacks of Modular Monolith:

  • a) Shared Runtime & Failure Domain: All modules still share the same memory space and process; a fatal exception, high CPU spike, or memory leak in one module can impact the entire system.
  • b) Coupled Deployment: Any update or bug fix in a single module requires redeploying the entire monolithic application.
  • c) Requires Architectural Discipline: Boundaries must be strictly maintained through conventions or architecture tests; without them, developers might be tempted to bypass boundaries over time.

6. Monolith vs. Microservices Architecture: What are the key differences and when to use which?

The Simple Analogy:

  • Monolith is like a Swiss Army Knife: Everything (knife, corkscrew, scissors, screwdriver) is housed inside one single pocket tool. It is convenient, easy to carry, and cheap to buy. But if the main spring snaps or the blade gets jammed, the entire tool is affected, and you can't easily replace just the scissors without disassembling the whole knife.
  • Microservices is like a Professional Toolbox: You have an independent hammer, an independent screwdriver, and independent pliers. If the screwdriver wears out, your hammer still functions perfectly. You can upgrade, fix, or replace the screwdriver anytime without touching the other tools.

What is Microservices Architecture?

Instead of building a single huge project, the application is divided into small, autonomous, specialized services (e.g., Auth Service, Product Catalog Service, Cart Service, Payment Service, Notification Service).

  • Each microservice has its own codebase and its own private database.
  • Each service can be written in a different programming language or framework if desired (e.g., Python for AI, .NET for high-throughput APIs).
  • Services communicate with each other over the network via HTTP/REST, gRPC, or asynchronous Message Brokers (like RabbitMQ or Apache Kafka).

When Should You Choose Which? (The Golden Rule)

Choose a Monolith when:

  • You are building a new startup, MVP (Minimum Viable Product), or proof-of-concept.
  • You have a small team (fewer than 10-15 developers).
  • The business domain is still evolving rapidly and you want fast iterations without distributed systems overhead.
  • You want straightforward local development, testing, and debugging.

Choose Microservices when:

  • The application is very large, complex, and has clear business boundaries.
  • You have multiple dedicated engineering teams that need to deploy independently without blocking one another.
  • Certain services have distinct resource requirements (e.g., intensive image processing vs. a simple user profile read).
  • Your company has mature DevOps, CI/CD, and container orchestration (Kubernetes) capabilities to handle the operational overhead.
